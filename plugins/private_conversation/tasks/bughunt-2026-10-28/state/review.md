## Candidate (P2, contract-dependent; PCV UI owner): stale browser page can end the newly active profile

**Observed behavior is confirmed; classify as a UI correctness defect if actions are intended to remain bound to the page the user saw.** The page embeds a hashed `data-playthrough-ref` on `<body>` (`server/index.php:482`), but the ARM and END forms contain only CSRF/action hidden fields (`:516-518`, `:550-553`). The server validates CSRF and submitted actor IDs (`:86-90`, `:141-156`) and checks only that the *current* key/catalog can stage (`:219-223`). It recomputes identity on each request (`:1042-1045`) and calls `pcv_stage($key, ...)` using that current key (`:1110-1123`). The form does not submit its rendered identity.

The client notices an identity change only after refresh, then clears actor selections (`server/assets/ui-refresh.js:283-300`). Refresh runs every 15 seconds (`:401-403`), skips hidden documents (`:344-347`), and runs asynchronously when a tab becomes visible (`:404-413`). END remains a separate enabled form (`index.php:548-554`); the visibility handler sets `serverAllowsArm=false` for the refresh, but does not gate END. Thus an A page can remain visually “Off” while B becomes active, and its old CSRF token can still submit END to B before refresh completes.

**Controller reproduction:** `stale_ui_end_post_repro.php` copies the actual `index.php`, `scope.php`, installation guard, and manifest into a task-local fixture; state, logger, and CHIM bootstrap are mocked, with a local PHP session. GET for profile A rendered “Off” and “End now.” The fixture then set profile B as current and active with an empty eligible roster, and POSTed only A’s session CSRF plus `action=end`. The actual controller returned HTTP 200 and called `pcv_stage` with B’s key and `['enabled' => false]`; A’s END form contains no identity field. Exit 0, raw output at `stale-ui-end-repro.output.txt`; exact command at `stale-ui-end-repro.command.txt`. The parallel ARM case also returned 200 and staged actor IDs 101/202 against B: `stale-ui-profile-repro.output.txt`.

**Impact and limit:** This does not cross the state key or expose A’s data; the B operation is still stored under B. It is a stale-page/misdirected-action risk, especially for END. The test proves controller routing, not a real browser race or a persistent state write: state is a spy, and no HTTP/game/server was used. Existing coverage verifies that a completed refresh clears selections (`tests/ui_refresh_check.mjs:358-363`) and that a GET refresh carries the hash (`tests/page_check.php:318-327`), but not a POST submitted before that refresh. If maintainers intend strict page-to-identity binding, the smallest guard is to submit the existing opaque page ref with both forms and reject a mismatch before staging; otherwise document that actions intentionally target whichever profile is current at submit time.

## Checked and excluded: group narrowing when wide presence is unavailable

This transition reproduces but is **not reported as a defect**. With a fresh close report/current input containing Aela and Bryn, a four-person active group, expired recent entries for Lydia/Faendal, and no wide report, `pcv_read_active_scene_npcs()` returns `wide_unavailable` for the two missing members while `error=false` (`server/state.php:1505-1506`, `:1580-1589`). The production caller therefore permits active drops (`server/scope.php:541-559`); `pcv_begin_request()` narrows and records the two left-scene IDs (`state.php:2447-2471`). The focused task-local receipt is `unavailable-wide-repro.output.txt` (exit 0; copied state/scope SHA256s are in the output). With `allowActiveDrops=false`, the same actual transition refuses and preserves all four IDs.

That output alone does not establish a broken policy: the 0.1.24 guide explicitly says unavailable Group members may be dropped while at least two eligible members remain (`distribution/private_conversation-v0.1.24.md:20`), and the resilience fixture treats a missing report as absence rather than a read error (`tests/scene_resilience_check.php:50-57`). The separate 0.1.24 release text reserves the database-error distinction for failed DB reads (`distribution/private_conversation-v0.1.24.md:30`). I found no source-backed promise that an absent/stale optional wide report must preserve members. The earlier malformed-close-report harness did not pass its logger setup and is not evidence; it remains recorded separately.

## Limits

All reproductions used the explicit retained Windows PHP 8.3.35 binary with `-n`, task-local files, and mocked state/logger/bootstrap only. No test suite, DB, HTTP service, game, provider, WSL, install, or live server was used. The stale-identity candidate needs maintainer confirmation of the intended form-submission contract before being promoted as a release blocker.
