# Private Conversation 0.1.19 ALPHA — compatibility review

Prepared 2026-10-16 from local source snapshots and an independent read-only inspection of the owner-built 0.1.19 package. I did not build the assets or perform a Plugin Manager install or runtime test.

## Findings

The CHIM Plugin Manager’s standard GitHub-release channel is compatible with the supplied root-flat `chim-plugin.tar.gz`: discovery sets `archive_strip_components` to `0`, while the installer stages and validates the extracted tree before generating its installed manifest (`plugin_discovery.php:419-440`; `server_plugin_installer.php:182-209`). The PCV builder’s current `flat_root=True` call agrees with that contract (`scripts/build-package.py:178-208,226-267,339`). The supplied archive passed independent member, metadata, checksum, and source-byte inspection, detailed below.

The manager resolves an existing folder by matching `git_repo` (or its recorded repository ID), so an existing `ext/private_conversation` installation should remain that folder on update. A fresh installation resolves to the repository package name, `ext/CHIM-PrivateConversation`. Generated metadata takes the full release tag for `version` and builds `config_url` from the resolved folder plus the staged root `index.php`; author-supplied values for these reserved fields are ignored (`plugin_discovery.php:923-968,1029-1068`; `server_plugin_installer.php:297-323`). Installation replaces the resolved directory through a backup/swap (`server_plugin_installer.php:233-250`), so users should update the existing entry rather than add a second folder. PCV’s private log directory includes a hash of the absolute extension path (`server/log.php:742-751`), and its state directory is nested under that root (`server/state.php:382-390`); a distinct folder therefore creates a separate storage identity.

The generated version string expected for the release is `private_conversation-v0.1.19` (28 characters). CHIM permits underscores in package tags, but PCV’s logger and diagnostics projection previously rejected `_`, turning this generated value into `unknown` or dropping the diagnostic row. I made the approved minimal compatibility fix: both existing 32-character allowlists now accept `_` (`server/log.php:610`, `server/log_reader.php:210`). No normalization or length-bound change was made. This is source-reviewed only; PHP execution was not authorized for this bounded change.

The PCV reflection loader first accepts an already-loaded compatible namespaced API, then falls back to the fixed `ext/mind_poisoning/reflection.php` path (`server/reflection.php:308-328`). The current local MP source’s `server/globals.php:4-5` loads its reflection API, and pinned CHIM core loads extension `globals.php` before request processing (retained core snapshot `main.php:61`). This makes the renamed fresh-install folder statically compatible when MP globals have run first. It does not prove installed load order or behavior in a live server.

The owner-built payload at `package-evidence/private-build-0.1.19` independently matched the current 20-file server allowlist. The flat discovery TAR contains the files directly at its root, including regular root `index.php` and `manifest.json`; all bytes and deterministic member metadata match source. The legacy TAR retains its `private_conversation/` wrapper. The DWPkg has 22 expected ZIP members, schema 4 and only `state` as a mutable path; its checksums and all server bytes match. The MO2 ZIP contains only `meta.ini` and the nested DWPkg, with exact byte equality and expected metadata. Its four asset hashes match `SHA256SUMS.txt`. Detailed member names, hashes, and assertions are in [package-inspection-0.1.19.md](compatibility-evidence/package-inspection-0.1.19.md).

The expected manager-installed version `private_conversation-v0.1.19` is 28 characters. Static inspection confirms the manager tag pattern and the two updated PCV 32-character logger/reader patterns admit it. This verifies the package/source boundary, not an actually generated installed manifest. The existing owner-run package-check receipt reports four passing tests; the inspected test `test_release_bundle_is_deterministic_and_matches_all_consumers` builds two temporary release bundles and compares every output byte-for-byte. I reviewed that source and receipt but did not rerun the test.

The reviewed local CHIM snapshot is the retained directory named `chim-plugin-review-f9cb8eb-…`; it has no Git metadata, so the complete upstream commit identity is not independently established here. Exact file hashes and source anchors are in [source-snapshot.md](compatibility-evidence/source-snapshot.md). The official [CHIM Plugin Guide](https://dwemerdynamics.com/chim/plugin-guide.html) documents the Plugin Manager archive and flat root layout. No provider, installer, WSL distro, live database, installed game, or production service was used for this review; the public guide was reviewed online.

## Remaining decisive checks

The archive/member/checksum checks now pass for the supplied build. Still unverified are an actual generated Plugin Manager manifest for both the same-repository existing folder and a fresh repo-name folder, controlled Plugin Manager installation, logger/reader PHP execution on the release payload, and installation/gameplay behavior. The release therefore has source-and-package compatibility evidence only; it does not establish installation or gameplay readiness.
