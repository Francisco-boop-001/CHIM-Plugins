For routine acceptance, use a disposable CHIM server and database plus a separate test client/profile/save. A separately authorized, backed-up test of a live release is a distinct bounded operation: record its target, backup, and rollback plan, and do not treat it as permission to touch unrelated production data or as beta/stable certification.

Record PCV version/install route, CHIM/server revision, client build, Mind Poisoning version/API and enabled state, and UTC start time. Back up test-server files/configuration, database, and client package/sync setup. Restore to a separate disposable target and confirm ordinary chat; if not tested, record **rollback unverified**.

For each check, record PASS / FAIL / NOT RUN, UTC time, versions/settings, observed behavior, and fixed event/outcome/reason codes from PCV Operational logs or Mind Poisoning diagnostics. If the operator directly confirms an outcome but an independent trace is absent or narrower, record it as operator-confirmed and state the missing detail; do not call that practical outcome NOT RUN solely for lack of correlated logs. NOT RUN means the outcome itself was not observed or confirmed. Do not include dialogue/audio; missing diagnostics do not substitute for a required technical invariant.

1. **Ordinary baseline.** With no PCV scene armed, send an ordinary Standard input and observe the response. Expected: CHIM handles it normally. Record the response path and any PCV routing entry.

2. **Pair and bystanders.** Select eligible A/B, enable **Exclude the player**, set **Other NPCs** to **Exclude from this conversation**, click **Arm or update on next input**, and send an ordinary Standard direction about C. Expected: A starts; supported rechat may stay with A/B per CHIM settings, and direction is instruction, not Player speech. Repeat with **Present but silent**; it adds generic scenery, not silence from vanilla greetings. Record mode/speakers. This cannot prove private history, model compliance or physical privacy.

3. **Solo and optional opinion effect.** Select eligible **Reflecting NPC** A in **Solo reflection**, exclude the player, click **Arm or update on next input**, and send ordinary Standard direction for A to think aloud. Expected: one response, no automatic continuation. With compatible, enabled MP, a correlated `committed` or `zero_change` result passes; no opinion delta is required. A documented policy skip/rejection matching the recorded settings, or absent/incompatible MP, makes the effect subcheck **NOT APPLICABLE**—not proof of integration; record its fixed reason. With MP enabled, missing/mismatched ACK or final outcome, registry/provider error, or failed/unconfirmed persistence is **FAIL / investigate**. An error log does not pass the check. `reflection.output_registered` alone is not an opinion result; record PCV and MP outcomes separately.

4. **Second reflection and repeat use.** For the timed interval/registration subcheck, use the first `reflection.output_registered` UTC time; after 61 seconds and before 600 seconds have elapsed, send a second distinct Standard direction with new material. Do not interrupt requests or manufacture a failure. With MP enabled, expect a second response, distinct registration tuple, and its own outcome; without compatible MP, mark only the opinion subcheck NOT APPLICABLE. A direct operator confirmation that repeat use succeeded is an accepted practical PASS even if the exact interval and per-turn IDs were not retained; state those limits rather than labeling basic repeat use NOT RUN. If the first was acknowledged, this tests repeat use. A distinct accepted registration while the first remains unclaimed is replacement evidence; the UI does not display lease status directly, so keep that lease-specific subcase separate unless diagnostics establish it. Missing registration/ACK or operational error with MP enabled is FAIL / investigate, not a valid skip.

5. **END, including stale eligibility and disable failure.** During an active scene, click **End now**, then send ordinary Standard input. On success, the scene ends and input follows normal CHIM handling; in-flight work/audio may finish. Separately, if an actor naturally becomes stale/unavailable, wait until PCV shows it, click **End now** without refreshing/editing reports, then send ordinary input. Expected: END works and stale scene state does not hold the next request. Record presence status/reason and routing outcome; if staleness cannot occur naturally, mark that subcase NOT RUN. If the disable result is unconfirmed, direct END and solo wrap-up must return the existing state-unavailable error, must not report `ended`/`off`, and must not forward the control phrase as dialogue. Pair/group wrap-up must stop before generating its closing turn. The targeted stubbed-hook fixture passed these caller-contract cases; it does not reproduce a real persistence fault or establish live failure behavior. Because the stage operation may fail after a write, report “could not confirm the scene ended; it may remain active”; do not infer whether stored state changed. For 0.1.20, a direct ordinary Standard input after END was separately operator-confirmed, and a later Standard rechat logged `scope_off`; see the evidence record. This does not cover the stale-eligibility or disable-failure subcases.

6. **Disable and remove.** Record the install route. Disable/remove PCV from that source using its supported client/manager controls, then use CHIM Plugin Manager **Delete** for the server copy. Sync/reload once; confirm PCV stays absent and ordinary Standard chat works. Do not edit ledgers, migration rows, tables or files by hand. Delete does not undo MP opinions or prove DB rollback; END/uninstall do not cancel in-flight work/audio. Database restoration is separate and must use the tested backup procedure. For 0.1.20, the operator confirmed removal caused no deleterious effects; the exact route and independent removal logs were not retained. Record that as operator-confirmed success, not proof of every route or of rollback/restoration.

Keep the completed record with the exact tested versions and dates. A failure report should include the step, expected/observed behavior, fixed codes and bounded relevant logs, not a full private transcript. No successful checklist run should be described as a privacy guarantee or as proof for a different server/client revision.
